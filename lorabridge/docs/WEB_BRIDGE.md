# Веб-мост и звонки (V2.9) — спецификация для EasyLink

Документ описывает мост между сервером и эфиром, который живёт в
Android-приложении EasyLink.

**Состояние на 2026-08-28: реализовано.** Код — в `EasyLink`:
`net/WebClient.kt` (транспорт), `repo/WebRepo.kt` (логика моста),
`audio/WebAudioBridge.kt` (перекодирование), `ui/screens/WebScreen.kt`
(настройка). На живом железе не проверялось.

## Роль телефона

Телефон в этой схеме не «клиент чата», а **мост**. У него три работы:

1. Зеркалить в веб то, что услышало радио, и наоборот.
2. Быть **шлюзом в эфир**: выносить в LoRa сообщения, отправленные из
   браузера тем, кого в вебе нет.
3. **Перекодировать звук** во время звонка: Opus/PCM из веба → AMR-NB
   для FSK и обратно.

Третий пункт живёт на телефоне не случайно. Сервер сознательно не
трогает содержимое звука: у Android уже есть и Opus, и AMR-NB в
`MediaCodec`, а поставить кодеки на веб-сервер значит держать там
ffmpeg и следить за его нагрузкой на каждом звонке.

```
браузер ──opus──┐                        ┌── браузер
                ├── сервер (только раздача)
браузер ──opus──┘         │
                          │ речь того, у кого слово
                          ▼
                  ТЕЛЕФОН-ШЛЮЗ  ← здесь перекодирование
                          │ AMR-NB по BLE
                          ▼
                    ESP32 → GFSK → эфир → тот, кто без интернета
```

## Подключение

```http
POST /lora-chat/api/login
{"uid":"<из персональной ссылки>", "password":"…",
 "node_id":"0x1A2B3C4D", "device_name":"Pixel 8",
 "hw_profile":"t3_v161", "has_fsk":true, "can_gateway":true}

→ {"ok":true, "token":"…", "member":{…}, "network":{…}, "peers":[…]}
```

`has_fsk` и `hw_profile` берутся у платы командой `get_radio` (см.
`docs/HWCFG.md`). Врать здесь нельзя: сервер по `has_fsk` решает,
можно ли вообще вывести звонок в эфир, и при `false` честно скажет
людям, что голос уйдёт только в веб.

`can_gateway` — согласие быть шлюзом. Разумно снимать его в роуминге и
при низком заряде: работа шлюзом означает постоянный сокет и радио в
приёме. Менять на лету: `{"op":"gateway","on":false}`.

Дальше — WebSocket на `/lora-chat/api/ws?token=…`. Обычный WebSocket,
не Socket.IO: хватит OkHttp.

## Сообщения

Приложение шлёт то, что набрал человек:

```json
{"op":"msg", "kind":"text", "text":"привет", "to":null, "ref":123}
```

`to` — id участника для лички, `null` — всем. В ответ приходит `sent`
с разбором маршрутов:

```json
{"op":"sent","ref":123,"msg_id":45,
 "routes":{"web":[2],"lora":[3],"gateway":11,"lora_blocked":false}}
```

`lora_blocked: true` означает, что часть людей сообщение **не
получит** — показывать это надо явно, а не прятать.

### Всё, что услышало радио — на сервер

```json
{"op":"lora_rx", "node_id":"0xAAAA0003", "packet_id":77,
 "kind":"text", "text":"иду домой", "name":"Рома"}
```

`packet_id` обязателен: сервер по паре (узел, packet_id) отбрасывает
повторы. Один пакет слышат все телефоны в радиусе, и без этого каждое
сообщение из эфира двоилось бы по числу шлюзов.

Тот же кадр можно послать обычным `POST /lora-chat/api/lora_rx` с
`Authorization: Bearer <token>` — на случай, если сокет отвалился.
Терять услышанное нельзя: для получателя это может быть единственная
копия.

### Команда «вынести в эфир»

Шлюз получает:

```json
{"op":"lora_tx", "msg_id":45, "kind":"text", "text":"Рома, ответь",
 "from_name":"Philip", "web_flag":true,
 "targets":[{"id":3,"node":"0xAAAA0003","name":"Рома"}],
 "has_media":false, "media_url":null}
```

При `web_flag` текст перед отправкой в эфир префиксуется `[WEB] `.
Это нужно человеку, у которого под рукой нет телефона: на мештастике
он увидит `[WEB] Philip: Рома, ответь` и поймёт, откуда сообщение и
почему оно короткое. Медиа в эфир не идёт — вместо него ссылка.

Отчитаться об отправке:

```json
{"op":"lora_tx_result", "msg_id":45, "ok":true}
```

## Звонки

### Начало

Любой веб-участник шлёт `{"op":"call_start","codec":1,"mode":1}`.
Сервер отвечает `call_state` всем участникам:

```json
{"op":"call_state","call":"c1756…-1","mode":1,"starter":1,
 "web":[1,2],"air":[{"node":"0xAAAA0003","name":"Рома"}],
 "floor":null,"gateway":11,"bridged":true,
 "note":"…текст проблемы, если что-то не так…"}
```

`air` — те участники сети, кого нет в вебе, но у кого есть узел в
эфире. Ради них и поднимается радио-плечо.

### Шлюз получает

```json
{"op":"call_air_start","call":"c…","mode":1,
 "web_codec":"opus","air_codec":"amr-nb",
 "targets":[{"id":3,"node":"0xAAAA0003","name":"Рома"}]}
```

По этой команде приложение обязано:

1. Дать плате `{"cmd":"ptt_start","mode":1,"node_id":"0xAAAA0003"}` —
   она захватит канал и уйдёт в FSK.
2. Сразу после — `{"cmd":"ptt_web","names":"Philip, Misha","n":2}`.
   Плата отправит FSK-кадр `0xA5`, и устройство человека в эфире
   покажет, что в разговоре есть люди из веба. Кадр идёт **внутри
   FSK-сессии**, а не по LoRa: к моменту, когда анонс дошёл бы по
   LoRa, участники уже переключились на FSK и не услышали бы его.
3. Начать перекодирование в обе стороны (ниже).

`{"op":"call_air_end"}` — отпустить радио: `{"cmd":"ptt_stop"}`.
Пропустить эту команду нельзя: плата останется в FSK и оглохнет для
обычного LoRa до срабатывания 30-секундного watchdog.

### Аудиокадры

Звук ходит **бинарными** кадрами WebSocket. Кадр Opus весит ~60 байт,
и обвязка base64 раздула бы поток на треть при 50 кадрах в секунду.

```
байт 0   0xA1  — маркер аудио
байт 1   флаги: бит0 = кадр пришёл из эфира
байт 2-3 id отправителя (uint16 BE; на приёме — заполняет сервер)
байт 4-5 seq (uint16 BE)
байт 6   кодек: 0 = PCM16 16 кГц LE, 1 = Opus, 2 = AMR-NB
байт 7   резерв
байт 8+  полезная нагрузка
```

**Кодек в звонке с эфирным плечом — всегда PCM16 16 кГц.** Как только
сервер поднимает радио-плечо, он переводит на PCM всех веб-участников
и сообщает об этом в `call_state` полем `codec` (0 = PCM16, 1 = Opus).
Причина в мосте: сырой PCM пережимается в AMR-NB без плясок с
codec-specific data, которых требует Opus в `MediaCodec`, а взять их из
потока браузера неоткуда. Пока звонок чисто веб-овый, участники
общаются Opus'ом — он вдвое экономнее.

**Из веба в эфир.** Шлюз получает кадры с `from_air = 0` (PCM16 16 кГц),
понижает до 8 кГц, пережимает в AMR-NB 4.75 кбит/с и отдаёт плате как
раньше: `{"cmd":"ptt_audio","d":"<base64 AMR-кадров>"}`.

**Из эфира в веб.** Плата отдаёт `{"evt":"ptt_audio","d":"<base64>"}`.
Шлюз декодирует AMR-NB, поднимает до 16 кГц и шлёт кадр с
`from_air = 1`. Такие кадры сервер принимает **только от
шлюза** — иначе любой участник смог бы подделать голос человека,
которого в вебе нет.

### Слово в эфире

Эфир полудуплексный: в один момент говорит ровно один. Веб-участники
могут перебивать друг друга сколько угодно, но в радио-плечо уйдёт
только речь того, кто держит слово. Слово берётся автоматически первым
же кадром и удерживается ещё 1.2 с после последнего — иначе пауза
между словами отдавала бы микрофон соседу.

Приложению обычно ничего делать не надо. Явно управлять можно так:

```json
{"op":"call_floor","take":true}
→ {"op":"call_floor","granted":false,"holder":2}
```

### Плата без FSK

Если `has_fsk = false`, звонок в эфир невозможен — сервер это увидит и
вернёт `note` с объяснением. Плата в этом случае на `ptt_start`
отвечает:

```json
{"evt":"ptt_state","state":"unsupported","reason":"no_fsk"}
```

Приложение по этому событию предлагает позвонить через веб. Для
владельца E220-платы веб — единственный способ говорить голосом.

## Медиа

```http
POST /lora-chat/api/media      (multipart, поле file)
→ {"ok":true,"media":{"id":7,"url":"/lora-chat/api/media/7", …}}
```

Затем обычное сообщение с `"media_id":7`. Лимиты: 50 МБ на файл, 2 ГБ
на сеть, медиа живёт 30 дней (текст — всегда). Файлы дедуплицируются
по SHA-256: пересланное фото не съедает квоту второй раз.

## Что уже сделано в приложении

| Файл | Что делает |
|---|---|
| `net/WebClient.kt` | Логин, WebSocket с переподключением, бинарные аудиокадры |
| `repo/WebRepo.kt` | Зеркалит эфир в веб, выносит веб в эфир, ведёт эфирное плечо звонка |
| `audio/WebAudioBridge.kt` | PCM16 16 кГц ↔ AMR-NB 8 кГц, два потока, свои очереди |
| `ui/screens/WebScreen.kt` | Адрес, uid, пароль, переключатель шлюза, состояние |
| `Prefs.kt` | `webEnabled`, `webUrl`, `webUid`, `webPassword`, `webToken`, `webGateway` |
| `proto/Proto.kt` | События `dev_hello` / `dev_data` / `dev_ack`, команды `ptt_web` / `devcmd` |

Чего в приложении пока НЕТ и что стоит доделать:

- медиа: загрузка фото и голосовых в веб (`POST /api/media`) — сейчас
  мост переносит только текст, SOS и показания датчиков;
- виджеты датчиков в интерфейсе телефона: данные уходят на сервер и
  видны в браузере, но своего экрана в приложении у них нет;
- адресная доставка при `lora_tx`: сейчас сообщение уходит
  широковещательно, хотя сервер присылает список целевых узлов. Для
  сети из нескольких человек это лишний трафик, но не ошибка.

## Что важно не сломать

- **`packet_id` в `lora_rx`.** Без него дедупликация вырождается в
  сравнение текстов, и два разных «ок» подряд склеятся в одно.
- **`ptt_stop` по `call_air_end`.** Забытый FSK = глухая плата.
- **`has_fsk` честно.** По нему принимается решение о звонке.
- **Отчёт `lora_tx_result`.** По нему в вебе гаснет «передаётся».
